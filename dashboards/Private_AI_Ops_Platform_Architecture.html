Purpose

The engineering system behind a services-first business

Private AI Ops is a managed AI operations firm — not a software company. The product is the implementation layer: playbooks, connectors, prompt libraries, private inference, and ongoing management. This document describes the internal platform that team builds and operates to deliver the SKU catalog reliably, at margin, and without exposing regulated client data. It complements the two existing architecture views — the private inference/RAG environment diagram and the four-layer business-technology stack (M365, HubSpot, QuickBooks) — by describing what the founder/dev team actually engineers.

Core build principle — encode the pattern, don't pre-build it. Per the Unified Strategy, the platform (Layer 4) is a Year 2+ initiative that begins only after services create a repeatable pattern worth encoding (decision gate G6: 10+ retainer clients, 2+ documented vertical playbooks, combined MRR > $25k). Phase 0–1 is deliberately manual with off-the-shelf tooling. Every component below is tagged with the phase it gets built.

Four planes of the platform

Acquisition & Client Surface

The four free vertical tools (Law / Dental / Property / Charter Brief), their Pro tiers, and — later — a client portal and co-branded partner collateral. This is the top of funnel and the only self-serve code.

Delivery & Orchestration Plane

Where retainer work is executed: the workflow engine, versioned prompt/playbook library, job scheduler, human-in-the-loop review console, and native docx/xlsx deliverable generation.

AI / Inference Plane

Model-tier router with public Claude API by default, private inference by exception. Azure-hosted private endpoints for the lighter infra SKUs; an owned GPU node (vLLM) only for RAG/Managed tiers, demand-gated.

Security, Compliance & Observability

Per-client isolation, zero-retention enforcement, Entra ID + MFA on every credential, Purview and structured audit logging, BAA/DPA gating, and the metering that feeds billing and per-client COGS.

Component notes

Workflow Engine

A workflow = an ordered set of steps (fetch context → prompt → tool call → format → review → deliver) bound to one client. Starts as structured config + Power Automate flows; becomes a real engine only when repetition justifies it (Phase 2).

Playbook / Prompt Library Service

The moat, as code. Every prompt is vertical-scoped, versioned, and traceable to the deployment it came from. Serves the Workflow Engine at run time; backed by the git Playbook Repo.

Model Router

Chooses the lowest-privilege model tier that can do the job and the route the client's SKU permits: public API, Azure private endpoint, or owned GPU node. Single decision point for cost and compliance.

Connector SDK

Turns each new client integration from a bespoke project into a configured instance: shared auth, retry, rate-limiting, and field-mapping. Directly drives "each onboarding faster than the last."

RAG Pipeline

Document ingestion → chunking → embedding → per-client vector namespace → retrieval. Managed vector DB first (Pinecone/Qdrant); self-host on the GPU node only for RAG/Managed-tier clients.

Review Console

Queue of generated deliverables awaiting human sign-off, with diff view and one-click regenerate. The enforcement point for the human-in-the-loop principle.

Sequencing

Build roadmap — tied to the strategy's decision gates

The platform is built behind the services, never ahead of them. Each phase ships only what the next tranche of signed revenue requires. Gates G1–G6 are from the Unified Strategy's decision-gate table.

  • Four free vertical tools live: static web app + Claude API budget tier + lead capture. Charter Brief Pro (React/TSX) already exists as the reference implementation.
  • Playbook Repo stood up in git — discovery scripts, first prompt patterns, SOP skeletons per vertical.
  • Security baseline: M365 Business Premium, Entra ID + MFA everywhere, 1Password, Purview logging on.
  • Legal gating scaffold: BAA/DPA/MSA templates (attorney-reviewed) referenced by a checklist that later becomes automated SKU gating.
  • Deliverable Apps + repo + defensible security posture — no bespoke backend yet.
  • Client Config Store + Workflow Engine v0: structured config + Power Automate/Zapier flows, not a custom engine.
  • Playbook Library Service: versioned prompts served into runs; every edit tracked to a client deployment.
  • Model Router v0: tier selection (budget/mid/premium) + token accounting → Metering DB.
  • Review Console (can start as a shared queue) enforcing human sign-off before delivery.
  • Deliverable Generator: native docx/xlsx output. Billing + CRM sync to QuickBooks / HubSpot.
  • Pro Tier auth + self-serve billing + primary-workflow automation + 48-hr outreach alert.
  • Deliverable Repeatable delivery of PAO-ONB-SM PAO-RET-SM PAO-PRO-STD at 30–50 hrs/onboarding.
  • Connector SDK: shared auth/retry/rate-limit/mapping. First real connectors — Clio, AppFolio/Buildium, Dentrix, QuickBooks, DocuSign.
  • Azure private-endpoint route in the Model Router → ships PAO-INF-END PAO-INF-BAA with no owned hardware.
  • Owned GPU node (vLLM, 4×RTX 4090) + RAG pipeline + per-client vector stores — only once G1 passes (≥1 MGD or ≥2 RAG signed). Ships PAO-INF-RAG PAO-INF-MGD.
  • Eval / Prompt Regression Harness — no prompt change reaches a live client untested.
  • Job Queue + Scheduler for batch workflows (recall runs, renewal batches). Monitoring + per-client COGS dashboard.
  • Deliverable Full infra SKU line + PAO-RET-MX; margin visibility per client.
  • Playbook Packager: reusable onboarding kits per vertical (prompt sets + connector configs + checklists) — turns tribal knowledge into a deployable artifact.
  • QLoRA fine-tune sprint tooling on the GPU node (add-on revenue, HIPAA-safe — data stays on node).
  • Playbook analytics: hours-per-onboarding trend, reuse rate, which workflows drive retention.
  • Deliverable Onboarding at 15–25 hrs; a second vertical delivered from a packaged playbook.
  • Client Portal: engagement status, monthly reports, workflow request intake, usage visibility.
  • AI Ops Control Plane: unifies workflow health, endpoint uptime, metering, billing, and playbook state in one internal surface.
  • Workflow monitoring surfaced to clients; partner referral portal + co-branded collateral for Tier-2 co-sell MSPs.
  • Evaluate a tightly-scoped vertical app marketplace — only if channel volume justifies it.
  • Deliverable The Layer-4 platform the Unified Strategy defers to Year 2+, now backed by a proven pattern.
Anti-goal. Do not build a workflow engine, a portal, or a control plane before services prove the pattern they should encode. The financial model reaches ~$602k Year-1 revenue at ~71.8% EBITDA margin with a $495–1,000/month tech run-rate — the platform investment is justified by scale, not anticipated before it.
Trust model

How client data moves through one engagement

The intended flow for a typical retainer workflow run. Every transition is isolated per client and logged as metadata (never prompt content) for billing and the monthly client report.

1 · Controlled intake

Client documents enter through a sensitivity-labelled SharePoint/OneDrive folder or direct upload — never email attachments as the primary channel. Intake event logged.

▼
2 · Workflow job created

Workflow Engine loads the client's config + the versioned playbook for this workflow. Connector Framework pulls any grounding context (matter record, patient list, lease data) via least-privilege API scopes.

▼
3 · Model Router decides tier + route

Lowest model tier that can do the job. Route per the client's SKU: public Claude API by default → Azure private endpoint for END/BAA → owned GPU node for RAG/MGD. RAG retrieval hits only that client's vector namespace.

▼
4 · Zero-retention execution

Inference runs inside a TLS tunnel; on the private routes, prompt + response live in GPU/endpoint memory only and are purged on response completion. Structured log records timestamp, client ID, workflow, token/latency — no prompt content.

▼
5 · Human-in-the-loop review

Draft deliverable lands in the Review Console. A person checks it, edits or regenerates, and approves. No output reaches the client unreviewed.

▼
6 · Delivery + metering

Native docx/xlsx returned through the Client Delivery Layer (SharePoint / portal). Usage record written to the Metering DB → rolls up into billing and the monthly client access report.

Three architectural decisions that matter most at this stage

Public API by default

Claude's API is the default execution path — dramatically cheaper and faster than owned infrastructure, and standard API terms already support the "no training on API data" posture most clients need. Private inference is the exception, not the norm.

Every credential MFA-enforced, vault-issued

A one- or two-person operation handling privilege- and HIPAA-adjacent data. The security baseline has to be genuinely defensible in a client conversation, not just described. Entra ID conditional access + 1Password on everything.

Native file formats end-to-end

Every deliverable is already docx/xlsx and the core environment is M365 — no format-translation step between internal production and client delivery. One fewer place for drift or a broken client experience.
